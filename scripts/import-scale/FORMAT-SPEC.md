# Import scale generator

This directory builds deterministic ZIPs for the Slate Part 2 import-scale proof. The committed inputs are the anonymized Notion workspace export (`tests/e2e/imports/fixtures/real/notion-workspace-export.zip`, 57 file entries) and Confluence Cloud export (`tests/e2e/imports/fixtures/real/confluence-space-export.zip`, 50 file entries). The Server/Data Center sample is a generated `entities.xml` ZIP derived from the Cloud page bodies and byte-exact Notion attachments because no exporter-produced Server/DC fixture was supplied.

Every JSON manifest and text report contains the exact provenance sentence:

> generated at scale from anonymised exports; no real large export was supplied

Generated archives live under the ignored `evidence/generated/imports/` directory. They are not committed fixtures. The generator records the exact ZIP path, archive byte count, entry list, file and directory counts, per-entry expanded/compressed sizes, expanded total, maximum entry size, and maximum per-entry compression ratio. It uses fixed timestamps, deterministic IDs/content and stable entry ordering. Payload data is streamed through bounded 64 KiB chunks; the 512 MiB inputs are never assembled as one expanded in-memory buffer. ZIP output is refused if it exceeds 256 MiB or if any entry exceeds the importer's 100:1 ratio limit.

Run under the repository's pinned Node/pnpm environment:

```sh
pnpm exec tsx scripts/import-scale/cli.ts --help
pnpm exec tsx scripts/import-scale/cli.ts --plan
pnpm exec tsx scripts/import-scale/cli.ts --group notion-scale --group cloud-csv-scale --group server-dc-entities --group boundary-20000 --group boundary-20001 --group boundary-512m --group boundary-512m-plus-one --group boundary-64m --group boundary-64m-plus-one
```

The default output and manifest directories are already guarded to `evidence/generated/imports/` and `evidence/imports/`. Use `--allowed-member-email` to select the named destination member for the one known Confluence source principal. It is an explicit mapping value recorded in the Cloud and Server/DC restriction specs; the generator never infers access from matching email text. A distinct unknown principal has no destination mapping and is expected to remain fail-closed.

## Independent source and physical counts

The expected-count formulas come from the committed fixture census, archive structure, deterministic generator formulas and known native persistence shape. They do not read parser output. `sourceExpected` describes source-level objects, `nativeExpected` describes physical native rows and revisions and is the independent pass/fail target, and `reportProjection` is contextual only. The Notion projection preserves the historical receipt baseline of 39 pages/35 versions and adds the generated Markdown pages; Cloud and Server/DC projections separately count imported source versions plus initial native revisions. Neither projection replaces physical `nativeExpected`. A generated manifest marks successful imports `provisional-awaiting-import-receipt`; measured importer receipts can be reconciled separately without replacing these expectations.

Source losses and destination-native adaptations have separate manifest fields. `sourceExpected.unsupportedConstructs` covers only source/parser losses and never includes an adaptation caused by the destination profile. The default status profile is `verification-only`: it seeds `rough-draft`, `in-progress`, and `ready-for-review` as active statuses without required verification, plus `verified` with required verification. Page import accepts only an exact matching active, non-verification-required key. The generators record raw page status counts and source IDs whose status therefore cannot be granted, along with the exact report item shape. They also record native warnings for closed restrictions and, for a personal Cloud space, its conversion to a private container.

For the Notion fixture, the source has 35 Markdown pages, 7 CSV databases, 22 records, 15 archive media objects and 57 files. Eighteen record rows match Markdown pages; four rows have no Markdown page. Native physical expectations count 35 Markdown pages + 4 detached record pages + 7 database backing pages = 46 page rows, with 46 initial page revisions. The 15 source media objects have 17 page-owned file copies. The pre-Part 2 receipt projected 39 pages and 35 versions because it counted the Markdown and detached record pages but omitted the 7 backing pages and their initial snapshots; that old projection is recorded separately and is not the physical success target. The scale archive adds 3,020 ordinary Markdown pages in 20 roots, 5 nested teams per root and 29 notes per team (`20 × (1 + 5 + 5 × 29)`). Thus it has 3,055 source pages, 3,066 physical pages/revisions, 7 databases, 22 records, 15 source media objects, and 17 baseline physical files.

Notion `_all.csv` has no declared source property schema. An independent census of the committed CSV headers and cells records 7 databases, 42 fields, 22 records and 110 structural record cells (60 populated, 50 blank). Value-derived source types are 7 title, 24 text, 4 select, 3 date, 2 email and 2 URL fields. Persistence maps title to text, so the expected native field type counts are 31 text, 4 select, 3 date, 2 email and 2 URL. The census preserves each table and column path, row/populated/null counts, distinct-value counts and inferred select options in the manifest. Its 17 empty text columns and 7 sparse text columns remain explicit inference warnings: empty values do not reveal a type, and sparse single-value columns cannot distinguish select from free text. These are source-derived field and cell counts, not importer receipt results. Matched Markdown record pages may supplement normalized record properties, so the manifest does not claim an exact persisted cell count from the source CSV alone. Source view metadata, two loose filtered CSVs, one duplicate database name, four absent archive images and four detached record pages remain named unsupported constructs. Filler files use `.txt`, which the Notion planner treats as `text/plain` media; their deterministic ASCII payloads are valid UTF-8. There are no explicit ZIP directory entries, so every ZIP member contributes to the documented file count.

For Cloud CSV, the source contributes three current pages, one draft source version, three page restriction rows of source type `EDIT`, and the fixture's supported/unsupported body content. The scale generator clones those rows and preserves their `EDIT` type 999 times, for 3,000 pages and 4,000 imported source versions; the native physical expectation adds 3,000 initial page revisions for 7,000 total. There are 2,997 generated global page labels. Of 3,000 restriction rows, 2,999 name the known principal and one isolated row names an unknown principal in place of that page's known grant. That gives 2,999 expected mapped grants and one unresolved, fail-closed restriction. The input has no local attachment content rows, so native media/files are zero. Source space permissions, roles and external image content remain explicit losses.

The generated Cloud CSV has 3,000 imported current page rows, all with raw `content_status=current`. None matches the default eligible status keys, so the report expectation has 3,000 destination-status loss items, each with label `current`, source ID `confluence-page:<contentid>`, and the exact shared status detail recorded in the manifest. This category is not added to `sourceExpected.unsupportedConstructs`. The raw `spaces` row is personal, so it also produces one native container warning for `confluence-space:163842` (label `alex`) when imported as a private container. Expected warnings total six: four source warnings, one native edit-restriction warning, and one private-container conversion warning.

Cloud `contentproperties.csv.gz` contains 28 source rows across 12 property names. The generated table has 16,012 rows: the original 28 plus 15,984 cloned rows across the selected page templates. The manifest and independent raw-byte census record every name and row count. `titleEmoji` has one source row and 1,000 generated rows; valid values on imported current pages map to native icons. The other 27 source rows and 15,012 generated rows are unsupported configuration retained in the original archive. The mapper reports one unmapped construct per distinct property name with lost rows, not one item per row: 11 source categories and 11 generated categories. Each detail carries the exact raw-row total split among unsupported, malformed and without-an-imported-current-page rows. These report-item counts are separate from row counts and do not imply general content-property fidelity. The category expectations are derived from raw source/generated CSV bytes and the documented mapping behavior, never copied from a preview or import report.

The Server/DC ZIP now has `entities.xml` and three bounded PNG attachment members copied byte-for-byte from the committed anonymized Notion export. The previous Version-only archive, generator manifest and census remain saved as before-history evidence. This is **generated at scale from anonymised exports; no real large export was supplied**. Cloud provides body excerpts but no attachment binaries; the XML object graph and numeric attachment layout are deliberately generated construct coverage, without a vendor-produced Server/DC export or standards-conformance claim.

There are 1,000 nested three-page trees: 3,000 current `Page` objects and 3,000 historical `Page` objects. Current pages list `historicalVersions`; historical pages point back through `originalVersion` and retain version 1, title, `versionComment`, `lastModificationDate` and `contentStatus=historical`. Both snapshots reference their own `BodyContent` objects, giving 6,000 bodies with distinct deterministic current/history markers. Every historical identity, owner, version, date, comment and body hash is recorded before the production parser is called. Expected native output is 3,000 current pages and 6,000 revisions, including the 3,000 initial current snapshots. The old standalone `Version` parser shape remains supported, but this scale archive no longer relies on it.

One global `Label` and 3,000 `Labelling` entities preserve the current-page labels. There are 3,000 current-page restriction sets and permissions: 2,999 name the known `ConfluenceUserImpl` and one names an unresolved source principal. Restrictions are explicitly mapped by the operator; historical source identities never activate accounts. The archive has 21,006 XML entities in total. Three `Attachment` entities have the same filename and distinct IDs, explicit `container` references, version 1 and `contentType=image/png`. Their bytes live at `attachments/<current-page-id>/<attachment-id>/1`. One entity names a historical owner alias. One attachment belongs to the unknown-principal page and two to known restricted pages. Storage-format `ac:image` / `ri:attachment` image references include their saved version; all three cross-owner `ac:link` attachment references carry nested `ri:page` titles (two with `ri:space-key`, one historical title in the referring owner's space). The 3,000 page links comprise 1,000 current titles with explicit `SCALE` space keys, 1,000 historical title aliases in the source owner's space, and 1,000 explicit historical content IDs with current titles and space keys. Thus 2,000 links exercise title resolution without IDs and 2,000 resolve historical aliases. Unique title candidates are scoped to exported spaces; explicit IDs can disambiguate a matching title, but missing IDs, contradictory references, ambiguous titles or unknown/ambiguous spaces remain reported text. Historical title aliases map only to their proven current owner. Owned images and sibling attachment links preserve the attachment entity's owner independently from link location. Each media manifest item records the exact committed Notion source path, byte length and SHA-256; native physical files remain three.

Only the 3,000 current pages carry status `current` into native status lookup. The expected report therefore contains 3,000 status losses, one unresolved-principal adaptation and one restriction warning, with zero source unsupported constructs. The independent census reads current/historical identities, reciprocal references, separate bodies, media coordinates and hashes, permission identities and status IDs directly from retained archive bytes. It records 9,004 physical creation-ledger items (one container, 3,000 pages, 6,000 revisions and three files), independently of preview or Completed output. Historical restricted bodies use the intersection of historical and current page permissions; any narrowing is reported against the affected current page and historical source IDs. Cycles, absent owners and conflicting history or attachment ownership are reported and never published as independent live pages or files. Native recovery access is retained.

The generated unknown principal's `userSubject` and `userName` use the same opaque source identity and reference no exported user object. The one-off restriction evidence separately covers duplicate set/user/permission objects, duplicate scalar content references, and contradictory user/group/username assertions, including an absent user object with a conflicting username. Those ambiguous inputs close every affected current or historical owner and report the exact source identities; they are not counted as safe generated-scale input.

## Archive boundary groups

| Group | Exact measured boundary | Expected result |
|---|---:|---|
| `boundary-20000` | 20,000 file entries, including the 57 source entries and zero-byte UTF-8 `.txt` media | Success at the inclusive file-count limit |
| `boundary-20001` | 20,001 file entries | Refusal: `The archive directory exceeds the import safety limits.` |
| `boundary-512m` | 536,870,912 expanded bytes across source entries and streamed `.txt` payloads | Success at the inclusive aggregate expansion limit |
| `boundary-512m-plus-one` | 536,870,913 expanded bytes | Refusal: `The archive expands beyond the import safety limits.` |
| `boundary-64m` | One added 67,108,864-byte `.txt` entry; maximum entry is exactly 64 MiB | Success at the inclusive per-entry limit |
| `boundary-64m-plus-one` | One added 67,108,865-byte `.txt` entry | Refusal: `The archive expands beyond the import safety limits.` |

Boundary manifests distinguish ZIP input inventory from native output expectations. For expected rejections, the native and import-report projections are zero because refusal precedes native publication; the manifest still records the full source archive entry inventory and byte totals. Accepted boundary fillers are unreferenced media and the current native persistence shape assigns those media to the first imported page; their media and physical-file counts are included in the independent expectations.

The refusal text is copied from the existing archive safety parser. The generator does not change import limits or rewrite those errors.
