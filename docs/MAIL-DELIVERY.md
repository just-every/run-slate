# Identity mail custody and recovery

Slate admits only sign-in and invitation mail. Migration `0008_identity_mail_outbox.sql` appends custody/scheduling fields to existing delivery rows and retains prior history. Token creation, AES-GCM encrypted immutable message, and invitation operation receipt commit in one D1 batch. The encryption key is derived with domain separation from SESSION_SECRET; the envelope is bound to workspace and delivery identity. Neither provider credentials nor plaintext links enter receipts, activity, status responses or portable archives. Mail, invitations, magic links and sessions remain excluded from exports. Changing SESSION_SECRET invalidates the existing custody and sessions.

Local development suppresses all mail silently when `LOCAL_DEVELOPMENT=true`, `MAIL_PROVIDER=development`, and `APP_URL` is an exact loopback origin. There is no captured-mail page. `rer dev` opens a key-gated local owner session; a signed-in local owner can export the workspace directly without email confirmation. Hosted startup rejects development mail. For authorized `rer deploy --environment production`, `SLATE_MAIL_PROVIDER` must be explicitly set to `resend` or `sendgrid`, with verified `SLATE_MAIL_FROM` and matching `SLATE_MAIL_API_KEY`. The native deployment adapter writes the selected provider and sender into the Base deploy-kit declaration; deployment stores the key as a Worker secret. There is no provider default. Base derives the deployed origin and runtime `APP_URL`. Local setup preserves the existing owner, private settings and database state.

One request makes at most one attempt. Cron resumes pending commands and abandoned 60-second claims. A retry cycle has at most three attempts with deadlines at admission, 150 seconds and 300 seconds; the one-minute cron may observe the second deadline late without shifting the third deadline. Provider downtime, cron downtime or backlog can delay execution; no wall-clock delivery guarantee is asserted. After exhaustion, a person can explicitly begin another bounded cycle, retaining the original message and provider key. A successful Resend receipt means provider acceptance, not inbox receipt.

Every attempt revalidates active member/link or the original inviter, exact unused invitation, pending grant, target access and guest switches. Claiming fences the current ACL epoch. Pending guest grants name the invitation until acceptance transfers that exact row to the new member. Revoking a pending grant cancels its invitation and delivery; revoking another invitation to the same address does not. Authority can change after the remote request has begun; the already-transmitted email cannot be recalled, but acceptance rechecks current authority and refuses invalid tokens.

Resend documents identical-payload idempotency keys retained for 24 hours: https://resend.com/changelog/idempotency-keys. Slate retries an uncertain result only within 23 hours of its first attempt, with the same immutable body and key. An HMAC fingerprint binds retries to the admitted provider credential. A different credential cannot safely assert the same provider account; restore the admitted credential or revoke the old invitation and create another. After the safe window, Slate clears encrypted delivery material and records the uncertainty rather than risk a duplicate send. A crash after provider acceptance is recovered by replaying this key; no exactly-once inbox claim is made. HTTP error status/category is retained, while raw error bodies are excluded because providers can echo signed links or secrets.

`GET /api/workspace/mail` shows owner delivery status and each ordinary member's own invitations. `POST /api/workspace/mail/:id/retry` rechecks current authorization and link validity. `/api/invitations/revoke` accepts an exact active unused invitation ID and operation key. Old failed rows without encrypted payload cannot be replayed: revoke the invitation and create a fresh one.

Sign-in callers generate and retain an unpredictable `requestKey` (32–160 characters) with `POST /api/auth/magic`. Repeating the email/key resumes the same delivery, including explicit retry after exhaustion. `POST /api/auth/magic/status` accepts that capability and email and returns only state, sanitized error, next attempt and retry availability; unknown capabilities return unconfirmed, never sent. The capability conveys no authentication authority. Browser callers should retain it across request-response loss, and generate a new key when deliberately requesting a new link.

Local evidence: actual SQLite fault-injection tests and Cloudflare Worker/D1 tests cover admission interruption, response loss, bounded scheduling, replay, current authority, exact guest grants, revocation and migration. Provider requests in tests use test-only doubles. Real authorized Resend delivery, provider-side idempotency behavior, live cron scheduling, bounce and inbox acceptance remain external acceptance work.
